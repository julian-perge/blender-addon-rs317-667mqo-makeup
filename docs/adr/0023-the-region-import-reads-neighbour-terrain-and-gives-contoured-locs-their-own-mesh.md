# The region import reads neighbour terrain, includes loc shadows and gives contoured locs their own mesh

On 2026-11-14 the Spec stage of issue 35 read the client rules that [ADR 0022](0022-the-region-import-checks-each-value-against-a-second-reader.md) left open, and the owner settled eight questions that the rules raised. The spec is `spec/35-draynor-region-import.md`. The client lines are in the 2018 Old School client that [Model format references](../research/model-formats.md) lists. The counts are in [Region 48_50 of snapshot 430](../research/region-48-50.md).

- **Edges.** The client blends the underlay colours of a tile over 11 by 11 tiles and lights each tile corner from the heights of its neighbours (`class24.java` lines 98 to 216). The tiles on the east and north edges of a region also need corner heights from the next region. The import reads the terrain of the 8 neighbour regions for their heights and underlays, and imports only the tiles of the chosen region. It does not read the scenery of the neighbours, so their loc shadows do not reach the edge corners. The alternatives were to read the neighbour scenery too, which needs 8 more keys, and to blend and light only from tiles inside the region, which gives colours unlike the game up to 5 tiles from the edge.
- **Contoured locs.** The client moves each vertex of a contoured loc to the terrain height under it (`ObjectComposition.java` lines 600 to 606). On a slope each placement then has its own shape. A contoured placement on uneven ground gets its own mesh. On flat ground it shares a mesh, because the client then returns the model unchanged (`ModelData.java` line 1152). This is an exception to the mesh sharing of ADR 0022. In region `48_50`, 1,329 of the 1,874 level 0 placements are contoured. The alternatives were to ignore the contour, so that floor decor and walls float above or sink into slopes, and to leave it for a later issue.
- **Loc shadows.** The client's terrain light subtracts a shadow that walls and objects write at the tile corners they cover (`PacketBuffer.java` lines 252 to 493). The terrain light includes it. The terrain colours therefore need the decoded landscape and the loc models first. The alternative was to light the terrain without shadows and add them in a later issue.
- **Impostors and animated locs.** An impostor placement shows the loc that the client picks when its varbit or varp is 0, the state of a new account (`ObjectComposition.java` lines 830 to 846). An animated loc shows its model with no animation. The alternatives were to leave both out, or to leave out only the impostors.
- **Origin.** The south-west corner of the region is at Blender (0, 0, 0). One game unit is one Blender unit, as in model import, so one tile is 128 units. The alternative was world coordinates, which put region `48_50` about 400,000 units from the origin.
- **Operator.** File > Import > RS Region (from cache), with region x and y properties that default to 48 and 50. Only region `48_50` is tested. The alternative was an operator that imports only `48_50`.
- **Texture brightness.** The import decodes textures at the Brightness preference, as face colours are shown. The alternative was the stored palette, as in `texture_dump.zip`.
- **Bridges.** They stay for a later issue, as the idea stage decided. Region `48_50` has 28 bridge tiles, and the import report names them.

The Spec stage also corrected two facts of ADR 0022 and `GLOSSARY.md`:

- A landscape key file is named by the region id, `x * 256 + y`, not by the group. The key of `l48_50` (group 617) is `keys/12338.txt`.
- One tile is 128 game units. The client's `getTileHeight` splits a position into a tile and an offset by 128 (`class264.java` lines 96 to 108).
